# 资源核对与缺项：12 例逐条表

表由脚本生成，不手工维护：

```bash
python scripts/check_content_assets.py --out docs/week4     # 写 docs/week4/atlas-asset-check.{md,csv}
python scripts/check_content_assets.py --out <临时目录>      # 只查看、不落文档
```

输出在 `docs/week4/atlas-asset-check.md`（人看）与 `atlas-asset-check.csv`（表格工具用）。
脚本读三样东西：`mobile/src/content/atlas.json`、交接包的 `01_catalog` 与 `02_vectors`、
`examples/recognition.samples.json` 与 `examples/catalog.real-subset.json`；只读，不写交接包。

## 1. 列的含义

| 列 | 怎么来的 | 什么算通过 |
| --- | --- | --- |
| `caseId` / `landslideId` | 内容文件 | `case-ls-XXXX` 与 `ls_XXXX` 编号一致 |
| `类型` | 内容文件 + 完整目录 | 文本里的 `type` 与目录 `type` 相同 |
| `目录关联状态` | `examples/catalog.real-subset.json` | 8 条公开编号显示“已在公开子集”，其余“仅在完整目录” |
| `公开影像状态` | `examples/recognition.samples.json` + `mobile/public/samples/*.png` | 文件存在且 SHA-256 与样例清单、`image_index.json` 都一致才显示“哈希一致” |
| `尺度来源` | 交接包 `image_index.json` 的裁片窗口 | 窗口边长 ÷ 224 与案例文本里的 m/像素 相差 <0.1 |
| `图幅` | `image_index.json` 的 `source_tiles` | 与案例文本的 `tile` 相同 |
| `引用状态` | 内容文件 | `citationLocator` 里带“PDF 第 … 页” |
| `缺项/负责人` | 上列任一不过 | 通过则“—”，否则写明缺什么、找谁 |

## 3. 缺项清单（4 例）

| 案例 | 缺什么 | 影响 | 负责人 |
| --- | --- | --- | --- |
| `ls_0591`（SL，6.57 km²） | 公开影像、公开目录记录 | 案例页只有文字；助手不能引用具体影像 | 崔亚鹏（公开范围）／滕佳杰（申请资源） |

| `ls_0688`（FL，210.84 km²） | 同上 | 同上 | 同上 |
| `ls_0592`（CL，581.46 km²） | 同上 | 同上 | 同上 |

这 4 例在页面上的表现是明确的：案例页提示“暂无公开影像：本案例只有文字说明与目录记录”，
类型页卡片带“暂无公开影像”标签，检索文本里写“公开影像：暂无（只有文字说明）”。

## 4. 为什么不补图

- 组内决定：**仓库不收录影像资源**。4 张裁片在交接包里确实存在，但公开仓库只保留 8 张已核准的 224 像素预览，
  其余影像留在私有交接目录；完整目录的坐标也不写进 JSON。
- 用私有影像补数会让“公开可核”的边界失效：图能在页面上看到，但别人复核不了来源。
- 4 例的价值在于说明覆盖范围与判读限制；补齐要走资源申请流程，不靠临时截图。

## 5. 复跑注意
